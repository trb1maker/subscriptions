# Правила работы с проектом

Учебный проект — несколько сервисов в одном репозитории. Бизнес-требования берутся из [TASK.md](TASK.md). Раскладка каталогов из раздела 6 задания этим файлом не отменена: дерево ниже — черновик, его ещё нужно утвердить.

## Репозиторий

Черновик раскладки сервисов, не решение. Общий технический код уже согласован: он лежит в `pkg`. Сгенерированные контракты остаются в `api/gen`.

```
/
├── api/                          # контракты, без бизнес-логики
│   ├── openapi/                  # внешний REST
│   ├── proto/                    # внутренний gRPC и события
│   └── gen/                      # сгенерированный код, руками не правится
├── pkg/                          # общий технический код
├── cmd/
│   ├── auth/
│   ├── gateway/
│   ├── subscriptions/
│   └── usage/
├── internal/
│   ├── auth/
│   │   ├── domain/
│   │   ├── app/
│   │   └── adapters/
│   ├── gateway/
│   ├── subscriptions/
│   └── usage/
├── db/
│   ├── auth/migrations/          # goose
│   └── subscriptions/migrations/
├── deploy/
│   └── docker-compose-dev.yml
└── tests/e2e/
```

Инфраструктура разработки — `deploy/docker-compose-dev.yml`. Корневой `docker-compose.yml` из задания не добавляем.

Команда сервиса — только сборка: прочитать конфигурацию, соединить адаптеры с use case, запустить процесс. Бизнес-решений в `cmd/` нет.

## Общий код

Повторяющийся технический код живёт в `pkg`, а не копируется по сервисам.

В `pkg` кладём:

- загрузку конфигурации из окружения;
- `log/slog`;
- HTTP- и gRPC-серверы, mTLS, восстановление после паники, дедлайны;
- пул PostgreSQL, клиенты Redis, NATS JetStream, ClickHouse;
- OpenTelemetry и Prometheus;
- общий graceful shutdown.

В `pkg` не кладём пользователя, организацию, тариф, подписку, лимит и правила их изменения. Это домен конкретного сервиса. Туда же не кладём сгенерированный код: он остаётся в `api/gen`.

Сервис импортирует только три вещи: свой код, нужные пакеты из `pkg` и сгенерированный код из `api/gen`. Чужой сервис импортировать нельзя. Связь между сервисами — только через контракт.

## DDD

Бизнес-логика устроена одинаково во всех сервисах.

| Слой | Содержимое | От чего зависит |
| --- | --- | --- |
| `domain` | сущности, объекты-значения, инварианты, доменные ошибки, интерфейсы репозиториев | стандартная библиотека, включая пакет `uuid`, и соседние пакеты своего `domain` |
| `app` | сценарии: что сделать по команде или запросу | свой `domain` и `pkg` там, где нужен технический примитив вроде времени или логгера |
| `adapters` | HTTP, gRPC, Postgres, Redis, NATS, ClickHouse | свой `app`, свой `domain`, `pkg`, `api/gen` |

Направление зависимостей одно: `adapters` → `app` → `domain`. `domain` не импортирует адаптеры, драйверы и фреймворки. `app` не импортирует `adapters`.

Интерфейс репозитория объявляется рядом с тем, кто им пользуется: порт чтения и записи — в `domain` или `app`, реализация — в `adapters`.

Доменные ошибки — обычные значения Go (`errors.New`, собственные типы). Адаптер на границе переводит их в код gRPC или HTTP. В домен не попадают `status.Error`, `pgconn.PgError` и коды HTTP.

## Контракты

Контракт описывается до реализации и лежит в `api/`. Хендлер подстраивается под контракт, а не наоборот.

- Внешний REST — OpenAPI в `api/openapi/<service>/v1.yaml`. Сюда входят маршруты Gateway, в том числе те, которые задание сейчас рисует на Auth и Subscriptions.
- Внутренний RPC — protobuf в `api/proto/<service>/v1/`.
- Асинхронные события — protobuf в `api/proto/events/v1/`. Имя события без полей контрактом не считается.
- Генерация — [buf](https://buf.build). Результат попадает в `api/gen` и не редактируется.
- Публичный пакет сервиса для другого сервиса не создаём. Клиент берёт сгенерированные типы и вызывает их через gRPC.

Изменение контракта — отдельное изменение схемы, затем кода. Поля событий и RPC не дописываются «по месту» в хендлере.

## Библиотеки

Если у задачи есть принятая ниже библиотека, свою обёртку с тем же назначением не пишем. Новую зависимость добавляем только когда в списке нет подходящей, и тогда же дописываем её сюда.

| Задача | Библиотека |
| --- | --- |
| HTTP-маршрутизация | `github.com/go-chi/chi/v5` |
| gRPC | `google.golang.org/grpc`, `google.golang.org/protobuf` |
| Контракты protobuf | `buf` |
| JWT | `github.com/golang-jwt/jwt/v5` |
| PostgreSQL | `github.com/jackc/pgx/v5` |
| SQL-запросы | `sqlc` |
| Миграции | `github.com/pressly/goose/v3` |
| Redis | `github.com/redis/go-redis/v9` |
| ClickHouse | `github.com/ClickHouse/clickhouse-go/v2` |
| NATS | `github.com/nats-io/nats.go`, JetStream |
| Конфигурация | `github.com/caarlos0/env/v11` |
| Логи | `log/slog`, только методы `*Context` |
| Метрики | `github.com/prometheus/client_golang` |
| Трассировка | `go.opentelemetry.io/otel`, экспорт OTLP в Jaeger |
| Идентификаторы | пакет `uuid` стандартной библиотеки |
| Деньги во внешних форматах | `github.com/shopspring/decimal` только в адаптерах. В домене цена — `int64` в минимальных единицах валюты |
| Валидация HTTP DTO | `github.com/go-playground/validator/v10` |
| Расписание | `github.com/robfig/cron/v3` |
| Ошибки | стандартные `errors` и `fmt.Errorf` с `%w` |
| Тесты | `testing`, `github.com/stretchr/testify`, `github.com/testcontainers/testcontainers-go` |

Не подключаем аналоги из этого ряда: Gin, Echo, GORM, ent, Zap, Logrus, Viper, Wire, Fx, `github.com/golang/protobuf`, `lib/pq`, `dgrijalva/jwt-go`, `github.com/pkg/errors`, `github.com/google/uuid`. DI-контейнер не используем: сборка в `cmd/` остаётся явной.

`math/rand` не используем. Для эмуляции ошибок берём `math/rand/v2`.

Логгер — переданный `*slog.Logger`. Пишем только `DebugContext`, `InfoContext`, `WarnContext`, `ErrorContext` и `LogContext`: в `context` лежат trace и идентификатор запроса, без него они в запись не попадут. Пакетные `slog.Info` и `fmt.Print` не используем. Секреты и пароли в логи не попадают.

## Линтер

Конфигурация — [`.golangci.yml`](../.golangci.yml). Она проверяет форматирование, разбор ошибок, запрещённые библиотеки и границы слоёв (`depguard`).

```bash
task fmt:check
task lint:check
```

Сгенерированный `api/gen` линтер не проверяет. Исправление стиля: `task fmt:fix` и `task lint:fix`.

`depguard` не заменяет ревью контрактов. Он ловит импорт чужого сервиса, драйвера из `domain` и адаптера из `app`.

## Что уже решено по заданию

- Квота клиента считается в сообщениях. Токены пишутся в аналитику и на допуск к генерации не влияют.
- Единственный внешний HTTP — Gateway. Регистрация, логин и вебхук публичные, остальное с JWT. Внутрь уходит gRPC, вебхук транслируется в RPC.
- Остаток лимита считает Subscriptions. В Usage уходит одна команда с уже посчитанным значением.
- `CheckLimit` пускает генерацию, пока остаток больше нуля. Параллельные запросы, уже прошедшие проверку, могут увести остаток в минус: это намеренный овердрафт, без резерва и saga. `MessageProcessed` всегда списывает одно сообщение. При продлении новый остаток равен `квота тарифа + min(0, текущий остаток)`.
- ClickHouse в Usage хранит и логи, и аналитические события в разных таблицах. Проекция лимита в Redis восстанавливается из событий: последнее установленное значение плюс число уникальных списаний после него.
- Изменяющие операции идемпотентны. У команды, события, вебхука и мутирующего запроса есть ключ идемпотентности. Повтор с тем же ключом не меняет состояние второй раз: ни остаток в Redis, ни запись в ClickHouse, ни платёж, ни подписку.
