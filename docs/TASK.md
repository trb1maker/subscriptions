# Техническое задание: Микросервисы на Go - Платформа подписок на AI-сервис

## 1. Цели проекта

Разработать учебный проект, демонстрирующий:
- Микросервисную архитектуру на Go
- Паттерны проектирования (CQRS, Event Sourcing)
- Построение высоконагруженных приложений
- Работу с распределенными системами и асинхронным взаимодействием

## 2. Архитектура

### 2.1 Компоненты системы

```
Пользователь → API Gateway (REST + JWT валидация)
                    ↓ mTLS
              ┌────┴────┐
              ↓         ↓
          Auth      Subscriptions
              ↓         ↓
              Usage ←───┘
                ↓
         NATS (брокер сообщений)
```

### 2.2 Технологический стек

- **Язык**: Go
- **Базы данных**: PostgreSQL (auth, subscriptions), Redis (usage - лимиты), Clickhouse (usage - события, аналитика)
- **Брокер сообщений**: NATS
- **Мониторинг**: Grafana (метрики), Jaeger (трассировка)
- **Контейнеризация**: Docker, docker-compose
- **Взаимодействие**: REST (внешние API), gRPC (внутренние API), mTLS (безопасность)

### 2.3 Принципы взаимодействия

- Внешние запросы проходят через API Gateway (проверка JWT)
- Внутренние сервисы общаются через gRPC с mTLS
- Асинхронные события публикуются в NATS
- Gateway не знает внутреннюю архитектуру сервисов
- Сервисы не знают, что их вызывает Gateway (только mTLS)

## 3. Компоненты

### 3.1 Auth Service

**Назначение**: Управление пользователями, организациями и аутентификация

**API**:
- REST API для управления пользователями и организациями
- JWT токен содержит:
  ```json
  {
    "sub": "user_id или organization_id",
    "type": "user или organization",
    "roles": ["admin", "user"],
    "iat": timestamp,
    "exp": timestamp
  }
  ```

**Данные**:
- PostgreSQL: таблицы `users`, `organizations`
- Пользователь может быть привязан к организации (B2B) или быть независимым (B2C)

**Эндпоинты**:
- `POST /api/v1/users` - регистрация
- `POST /api/v1/login` - аутентификация
- `POST /api/v1/organizations` - создание организации
- `GET /health` - проверка здоровья (PostgreSQL)

### 3.2 API Gateway

**Назначение**: Единая точка входа, аутентификация, маршрутизация

**Функции**:
- Валидация JWT токенов для внешних запросов
- Проверка вебхуков (заголовок `X-Webhook-Key`)
- Пропуск запросов к соответствующим сервисам через mTLS
- Эмуляция AI-генерации (задержка + случайные ошибки)
- Проверка подписки и лимитов перед генерацией

**Эндпоинты**:
- `POST /api/v1/generate` - генерация ответа AI
- `POST /webhooks/payments` - обработка платежей
- `GET /health` - проверка здоровья

**Логика обработки генерации**:
1. Валидация JWT
2. gRPC запрос в `subscriptions` - проверка подписки
3. gRPC запрос в `usage` - проверка лимита
4. Эмуляция AI (задержка 30-90 секунд, 5% вероятность ошибки)
5. Асинхронная публикация события в NATS:
   - `MessageProcessed` (при успехе)
   - `MessageFailed` (при ошибке)
6. Возврат результата пользователю

### 3.3 Subscriptions Service

**Назначение**: Управление подписками и тарифами

**API**:
- REST API для управления подписками
- gRPC API для проверки подписки

**Данные**:
- PostgreSQL: таблицы `tariffs`, `subscriptions`

**Структура тарифа**:
```sql
CREATE TABLE tariffs (
    id UUID PRIMARY KEY,
    name VARCHAR NOT NULL,
    monthly_price DECIMAL NOT NULL,
    message_limit INTEGER NOT NULL,
    type VARCHAR NOT NULL,  -- 'b2c' или 'b2b'
    is_base_tariff BOOLEAN DEFAULT FALSE
);

CREATE TABLE subscriptions (
    id UUID PRIMARY KEY,
    user_id UUID NULL,
    organization_id UUID NULL,
    tariff_id UUID NOT NULL,
    status VARCHAR NOT NULL,  -- 'active', 'suspended', 'expired'
    current_period_start TIMESTAMP NOT NULL,
    current_period_end TIMESTAMP NOT NULL,
    payment_id VARCHAR NULL,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

**Логика**:
- B2C: ежемесячное списание, переход на базовый тариф при неоплате
- B2B: общий лимит на организацию, не переводятся на базовый тариф
- При смене тарифа: неиспользованный лимит платного тарифа переносится, базового - сгорает
- Cron-джоба для проверки истекших подписок

**События в NATS**:
- `PaymentReceived` - успешный платеж
- `PaymentFailed` - неудачный платеж
- `SubscriptionChanged` - смена тарифа
- `SubscriptionPeriodEnded` - окончание периода

**Эндпоинты**:
- `POST /api/v1/subscriptions` - создание подписки
- `PUT /api/v1/subscriptions/{id}` - изменение подписки
- `GET /api/v1/subscriptions/{id}` - получение подписки
- gRPC `CheckSubscription` - проверка валидности подписки
- `GET /health` - проверка здоровья (PostgreSQL, NATS)

### 3.4 Usage Service

**Назначение**: Учет потребленных ресурсов и управление лимитами

**Паттерны**: CQRS + Event Sourcing

**Данные**:
- Redis: текущие лимиты (Read Model)
  - B2C: `limit:user:{user_id}`
  - B2B: `limit:org:{organization_id}`
- Clickhouse: события и аналитика (Event Store)
  - Таблица `events`: все события системы
  - Таблица `payments`: информация о платежах
  - Таблица `token_usage`: фактические затраты токенов

**CQRS логика**:
- **Command** (запись): события из NATS обновляют Redis и Clickhouse
- **Query** (чтение): 
  - Быстрая проверка лимита из Redis (gRPC)
  - Аналитика из Clickhouse

**События в NATS (подписка)**:
- `MessageProcessed` - успешная генерация
- `MessageFailed` - ошибка генерации
- `PaymentReceived` - платеж (пополнение лимита)
- `SubscriptionChanged` - смена тарифа
- `SubscriptionPeriodEnded` - сгорание лимита

**Логика обработки событий**:
- `MessageProcessed`: 
  - Атомарный декремент лимита в Redis (Lua-скрипт)
  - Запись события в Clickhouse
  - Запись токенов в таблицу `token_usage`
- `MessageFailed`:
  - Запись события в Clickhouse
  - Запись токенов в таблицу `token_usage`
  - Лимит не декрементируется
- `PaymentReceived`:
  - Установка нового лимита в Redis
  - Запись платежа в Clickhouse

**Овердрафт**:
- Допускается (для LLM с долгой генерацией)
- Компенсируется в следующем периоде при продлении подписки

**Атомарность в Redis**:
```lua
local current = redis.call('GET', KEYS[1])
if tonumber(current) >= tonumber(ARGV[1]) then
    return redis.call('DECRBY', KEYS[1], ARGV[1])
else
    return -1 -- недостаточно лимита
end
```

**Синхронизация**:
- При старте: агрегация из Clickhouse → загрузка в Redis
- Периодически: сверка Redis и Clickhouse

**Эндпоинты**:
- gRPC `CheckLimit` - проверка доступных ресурсов
- `GET /health` - проверка здоровья (Redis, Clickhouse)

## 4. Обработка платежей

### 4.1 Схема работы

```
Платежная система → Gateway (/webhooks/payments)
                         ↓
              Проверка заголовка X-Webhook-Key
                         ↓
              Пропуск в Subscriptions
                         ↓
              Subscriptions обрабатывает платеж
                         ↓
              Публикация PaymentReceived в NATS
                         ↓
              Usage обновляет лимит и сохраняет платеж
```

### 4.2 Безопасность

- Gateway проверяет секретный ключ в заголовке `X-Webhook-Key`
- Subscriptions валидирует структуру вебхука
- mTLS для внутреннего общения

## 5. Мониторинг и observability

### 5.1 Метрики (Prometheus + Grafana)

**Технические**:
- `http_requests_total{service, endpoint, status}` - количество запросов
- `http_request_duration_seconds{service, endpoint}` - время ответа
- `http_request_errors_total{service, endpoint, error_type}` - ошибки
- `service_healthy{service}` - здоровье сервиса

**Бизнес-метрики**:
- `messages_consumed_total{type}` - списанные сообщения
- `tokens_used_total{type}` - затраченные токены
- `overdraft_count{type}` - овердрафты
- `payments_total{status}` - платежи

### 5.2 Трассировка (Jaeger)

- Сквозная трассировка от gateway до всех сервисов
- Визуализация времени выполнения каждого шага
- Correlation ID для связывания логов

### 5.3 Логи (Clickhouse)

- Структурированные логи в формате JSON
- Хранение в Clickhouse для быстрого поиска
- Связь с trace_id для корреляции с трассировкой

## 8. Критерии успеха проекта

1. Все сервисы работают независимо и общаются через определенные контракты
2. Лимиты корректно управляются (учитываются овердрафты)
3. События корректно обрабатываются через Event Sourcing
4. Система масштабируется (демонстрация через нагрузочное тестирование)
5. Мониторинг показывает ключевые метрики
6. E2E тесты покрывают основные сценарии использования
